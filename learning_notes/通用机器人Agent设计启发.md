# 从 3v3 足球项目学习通用机器人 Agent 设计

## 1. 核心结论

这个项目最值得学习的不是具体的足球战术，而是它已经形成了一个小型机器人 Agent 的基本闭环：

```text
传感器 / ROS / SDK
        ↓
平台适配与数据源
        ↓
只读世界快照 Context
        ↓
安全与可行动性检查
        ↓
情境判断与多机器人任务分配
        ↓
单机器人技能
        ↓
路径规划与运动控制
        ↓
机器人执行后端
```

将足球相关概念替换成通用任务、通用技能和通用世界模型后，这套分层可以作为巡检、配送、仓储、陪伴等机器人 Agent 的执行内核。

## 2. 值得借鉴的设计

### 2.1 世界状态与平台数据解耦

ROS 数据先进入 `WorldSnapshot`，再由运行时进行新鲜度过滤，形成每个控制周期使用的不可变 `Context`。

相关代码：

- `src/framework/types.py`：定义 `Context`、`WorldSnapshot` 等数据契约。
- `src/framework/runtime.py`：构造当前周期的 `Context`，过滤陈旧数据。
- `src/framework/ros_source.py`：把 ROS 消息转换成框架内部数据。

这样做的价值是：

- 策略代码不依赖 ROS topic、QoS 或具体 SDK 类型。
- 可以替换传感器、仿真器和机器人平台，而不重写上层决策。
- 陈旧数据会变成“未知”，避免机器人把历史位置误认为当前位置。

通用化后的世界模型可以包含：

- 机器人状态：位姿、速度、电量、温度、关节、故障。
- 环境状态：地图、障碍物、人物、物品和语义区域。
- 任务状态：当前目标、约束、优先级和截止时间。
- 数据质量：时间戳、置信度、坐标系和数据来源。

### 2.2 当前事实与跨周期记忆分离

项目把当前可观察事实放在不可变的 `Context` 中，把跨帧状态放在 `store` 或 `Player` 对象中，例如：

- 上一个比赛阶段。
- 当前进攻者。
- 锁定的开球机器人。
- 踢球迟滞状态。
- 避障方向记忆。

可以抽象为：

```text
Context = 当前可观察事实
Memory  = 历史、承诺和正在执行的动作
Goal    = 希望世界达到的状态
```

通用版本中，建议使用有明确字段和类型的 `AgentMemory`，而不是不断向 `SimpleNamespace` 动态添加属性。

### 2.3 决策层与技能层分离

`src/main.py` 负责判断比赛情境和分配角色，`src/player.py` 负责单个机器人如何完成动作。

这对应三个不同问题：

- 决策层：当前应该做什么？
- 分配层：应该由哪台机器人做？
- 技能与控制层：机器人具体怎样完成？

通用机器人可以把足球技能替换为：

- `navigate_to`：导航到目标位置。
- `follow_person`：跟随人员。
- `inspect_object`：检查目标。
- `pick` / `place`：抓取和放置。
- `dock`：回充电桩。
- `recover`：从故障或跌倒中恢复。
- `wait` / `speak`：等待和人机交互。

### 2.4 先检查能否行动，再分配任务

每个周期开始时，项目会处理跌倒、模式切换、处罚和位姿丢失，然后只将可行动机器人交给角色分配逻辑。

这可以进一步抽象为独立的 `SafetySupervisor`，负责：

- 急停和碰撞风险。
- 跌倒、过热和低电量。
- 定位失效和通信断开。
- 禁入区域和速度限制。
- 动作执行超时。
- 控制命令有效期。

安全层应该拥有否决上层任务和强制停车的权限。

### 2.5 快速控制循环与慢操作分离

项目的主控制循环按固定频率运行，切换模式和起身等慢操作则由后台 worker 执行，避免阻塞实时决策。

通用版本应给动作定义统一生命周期：

```text
PENDING → RUNNING → SUCCEEDED
                  → FAILED
                  → CANCELLED
                  → TIMEOUT
```

每个动作还应声明：

- 前置条件和成功条件。
- 失败原因。
- 超时时间。
- 是否允许抢占。
- 占用的资源，例如底盘、机械臂或相机。

### 2.6 全局规划与局部反应结合

当前项目使用 A* 生成全局路径，无法生成路径时回退到局部方向扫描，再由速度控制器执行。

```text
任务目标 → 全局路径 → 局部避障 → 速度控制
```

这是一个可以直接迁移到其他移动机器人的导航结构。全局规划处理整体可达性，局部规划处理动态障碍和即时变化，控制器负责把路径转成机器人指令。

### 2.7 用迟滞和角色粘性抑制抖动

项目没有在每一帧都无条件更换进攻者，而是使用距离余量保留当前角色；踢球状态也采用不同的进入和退出阈值。

同样的思想可以用于通用 Agent：

- 目标切换迟滞。
- 路径重规划冷却时间。
- 任务最短持有时间。
- 状态连续确认次数。
- 失败重试的退避时间。

这些机制可以避免机器人在多个近似选择之间来回切换。

### 2.8 可观测性属于 Agent 的一部分

项目提供动作标签、路径、目标点、朝向、心跳日志等调试信息。机器人系统出现问题时，需要回答的不只是“机器人做错了”，还包括：

- 它当时看到了什么？
- 它判断自己处于什么状态？
- 为什么选择这个任务？
- 技能执行到哪一步？
- 哪个安全条件阻止了动作？

因此，日志、指标、事件记录、轨迹回放和可视化应与决策代码同时设计。

## 3. 当前项目不宜直接照搬的部分

当前代码仍是面向足球比赛的简化框架，距离真正通用的机器人 Agent 还有一些差距：

- 状态机集中在 `main.py`，任务类型增加后会迅速膨胀。
- `Player` 同时包含技能、路径规划和运动控制，职责较多。
- 动作缺少统一的状态、失败原因、超时和取消语义。
- 世界模型依赖仿真真值，缺少协方差、目标跟踪、预测和传感器融合。
- 多机器人分工主要依据距离，未考虑能力、电量、风险和预计耗时。
- 后台慢操作使用单槽覆盖式意图，尚不支持优先级和资源仲裁。
- 项目没有自动化测试、场景回放和故障注入机制。

一个值得注意的边界情况是：球数据可能因为超时而变成 `None`，但部分支援逻辑默认球一定存在。这说明通用技能必须显式声明并检查前置条件，不能依赖跨层的隐含假设。

## 4. 建议的通用机器人 Agent 架构

```text
用户目标 / 调度系统 / 大模型规划器
                 ↓
Task Executive
任务图、行为树或分层状态机
                 ↓
Task Allocator
根据能力、距离、电量和风险选择机器人
                 ↓
Safety Supervisor
验证、否决、限速和降级
                 ↓
Skill Runtime
导航、抓取、观察、交互和恢复
                 ↓
Command Arbiter
仲裁底盘、机械臂和相机资源
                 ↓
Robot Backend
Booster、ROS、仿真器或其他硬件
```

建议优先抽象以下五个接口：

1. `WorldModel`：提供统一、带时间和置信度的世界状态。
2. `SafetySupervisor`：判断当前允许执行哪些动作。
3. `Skill`：封装一个可执行、可取消、可报告状态的能力。
4. `ActionResult`：统一动作状态、失败原因和执行信息。
5. `RobotBackend`：隔离具体机器人 SDK 和控制协议。

## 5. 大模型在机器人 Agent 中的位置

如果未来加入大模型，适合让它负责：

- 理解自然语言目标。
- 把复杂目标拆成有类型的任务计划。
- 根据任务结果进行高层调整。
- 解释机器人为什么做出某个选择。

不适合直接让大模型负责：

- 高频底盘速度控制。
- 急停和碰撞判断。
- 关节级实时控制。
- 绕过确定性安全约束。

更稳妥的边界是：大模型生成结构化任务计划，执行器验证计划，确定性技能完成实时动作，安全层始终拥有最终否决权。

## 6. 后续学习与改造顺序

1. 为 `Context` 增加机器人健康状态和数据置信度。
2. 定义统一的 `Skill`、`ActionStatus` 和 `ActionResult`。
3. 将跌倒恢复、模式切换等逻辑抽成 `SafetySupervisor`。
4. 把足球状态机改造成可组合的任务执行器。
5. 为多机器人任务分配增加能力、电量、耗时和风险成本。
6. 建立世界快照录制、离线回放和纯逻辑测试。
7. 最后再接入自然语言或大模型规划层。

## 7. 一句话总结

这个项目适合作为通用机器人 Agent 的“执行内核原型”：保留它的平台隔离、世界快照、周期执行、技能封装、安全降级和可视化思路，再逐步补上标准动作协议、任务执行器、资源仲裁、可靠性测试和更完整的世界模型。
