# 展厅机器人大脑需求文档

## 1. 文档信息

- 产品名称：展厅机器人大脑（暂定）
- 文档状态：MVP 需求定义
- 目标平台：轮式移动操作机器人（轮式底盘 + 机械臂/末端执行器）
- 目标环境：受控展厅
- 核心方案：VLM 环境理解 + LLM 判断与任务编排 + 已封装技能 API

## 2. 用户选择摘要

本需求基于以下已确认条件：

- 机器人用于展厅接待。
- 硬件形态为轮式移动操作机器人，默认由轮式底盘、机械臂和末端执行器组成；具体轮型、机械臂数量和自由度待硬件选型确认。
- 第一版支持多轮语音对话、自然语言理解、拿取并递交物品、轮式导航、开关门、预定义交互动作，以及回答环境相关问题。
- 导航、抓取、开门、递交和交互动作等底层技能 API 假设已经可用。
- 感知输入包括 RGB、深度、麦克风、激光雷达、机器人位姿/轮式里程计、嗅觉和末端执行器触觉。
- 用户主要通过语音与机器人交互；机器人通过语音、底盘/传感器头朝向和已注册交互动作提供反馈。
- 低风险动作可自主执行，敏感或高风险动作执行前需要用户确认。
- 记忆范围为当前任务和短期环境状态，不建设跨任务长期记忆。
- 第一版要求具备人员/障碍物碰撞保护、台阶及跌落边缘保护、坡度与防倾覆约束、禁区约束、模型或感知异常制动停车，以及高风险技能执行前确认。
- MVP 在受控环境中的端到端任务成功率目标为不低于 80%。

## 3. 问题定义

### 3.1 要解决的问题

现有机器人通常已经拥有导航、抓取、开门和动作播放等独立能力，但缺少一个能够理解自然语言、理解当前环境、组合多个技能、检查执行结果并在失败后调整计划的统一“大脑”。

本项目要解决的问题是：

> 在受控展厅中，让轮式移动操作机器人通过多轮对话理解用户意图，根据多模态环境信息形成可验证的当前状态，选择并编排已有技能 API，安全地完成多步骤任务，并能在执行过程中接受打断、反馈进度、解释结果和处理常见失败。

典型任务示例：

> 用户说“去展柜旁拿一瓶水给我”。机器人确认目标，导航至目标区域，定位可抓取的水，完成拿取，返回用户位置并递交；任何步骤失败时停止后续动作，并根据失败原因重新观察、重试或请求用户帮助。

### 3.2 VLM 与 LLM 替代的部分

VLM 与 LLM 主要替代当前足球项目 `main.py` 中人工编码的“情境判断、角色/任务选择和流程编排”逻辑：

- VLM 从视觉输入中识别物体、人员、门、区域、属性和语义关系。
- LLM 理解用户目标并基于最新 `CapabilitySnapshot` 提出由当前可用且已注册技能组成的完整任务计划；确定性任务执行器负责接受计划、推进步骤，并仅在计划失效时请求重新规划。
- LLM 只能从注册的技能集合中选择动作，不能直接生成轮速/底盘速度、机械臂关节角度或执行任意代码。

### 3.3 不被替代的部分

下列能力仍由确定性模块负责：

- 传感器驱动、相机标定、坐标变换和时间同步。
- 深度、激光雷达、轮式里程计等几何信息处理。
- 当前任务和短期环境状态维护。
- 技能参数校验、执行、取消、超时和资源仲裁。
- 碰撞保护、跌落边缘/台阶检测、坡度与防倾覆检查、禁区检查、失效制动停车和高风险动作确认。
- 轮式底盘控制、导航控制、机械臂控制、末端执行器控制和其他实时闭环控制。

因此，本项目不使用 VLM/LLM 完全取代状态管理。世界、对话、任务和系统健康状态分别由明确的模块维护，再按需组装为轻量、结构化、只读的 `AgentContext`。

## 4. 产品目标与非目标

### 4.1 MVP 目标

1. 用户能够通过语音下达受支持的展厅任务。
2. 机器人能够结合视觉和其他传感器理解当前任务环境。
3. LLM 能够将任务转换为受约束、可检查的计划提案，并由任务执行器校验和接受。
4. 任务执行器能够根据每个技能的成功或失败结果继续、有限重试、重新观察、请求重规划或请求帮助。
5. 任何大模型输出都必须经过执行器和安全层验证。
6. 在约定的受控场景测试集中，端到端任务成功率不低于 80%。
7. 用户可以在任务执行过程中询问进度、修正任务或要求停止，机器人应给出明确反馈并安全响应。

### 4.2 MVP 非目标

- 不训练端到端机器人基础模型或学习型动力学世界模型。
- 不让大模型直接控制电机、轮速/底盘速度或机械臂关节位置。
- 不支持任意开放环境和从未验证过的技能。
- 不建设跨天、跨用户的长期记忆和用户画像；对话上下文仅在当前会话和当前任务中保留。
- 不允许模型动态生成并执行代码。
- 不以完全无人监管运行作为第一版目标。

## 5. 目标用户与使用环境

### 5.1 目标用户

- 展厅访客：通过语音提出取物、递交、引导、问答和动作展示请求。
- 展厅工作人员：配置禁区、可操作物品、技能权限和演示流程。
- 开发及运维人员：查看感知结果、计划、技能状态、失败原因和安全事件。

### 5.2 环境假设

- 展厅地图、主要区域和固定设施已配置。
- 光照、噪声和人员流动处于可测试范围。
- 可拿取物品、可操作门和交互区域具有稳定标识或可感知特征。
- 机器人仅在已测绘、平整且满足底盘宽度、转弯半径、离地间隙和额定坡度要求的无楼梯区域运行；门槛、坡道、玻璃边界和跌落边缘需预先标注或可被安全传感器可靠检测。
- 底层技能 API 已在机器人平台上通过单项测试。
- 网络不可用或模型服务异常时，机器人必须停止当前高层任务并进入安全状态。

## 6. MVP 使用场景

### 6.1 自然语言任务

用户通过语音提出任务，系统完成语音识别、意图理解和必要的参数补全。当目标、位置或对象存在歧义时，机器人必须先追问，不能自行猜测关键参数。

### 6.2 多轮对话与交互

机器人应支持围绕当前会话和任务进行连续对话，而不是把每句话都当成互不相关的新指令。至少包括：

- 会话开始和结束：识别用户正在与机器人交互，并在超时或明确结束后关闭会话。
- 轮次管理：判断用户说话是否结束，避免机器人与用户同时持续说话。
- 指代消解：结合当前视觉焦点和短期对话理解“这个”“那个门”“刚才的水”等表达；证据不足时追问。
- 澄清与确认：目标不唯一、参数缺失或动作风险较高时，通过对话取得明确答案。
- 进度反馈：在任务开始、长时间执行、重试、完成和失败时给出简洁反馈。
- 任务中问答：用户可询问“你在做什么”“为什么停了”“还要多久”等当前任务问题。
- 打断和修改：用户可说“停下”“先别拿”“换成右边那瓶”等；执行器应安全暂停、取消或重新规划。
- 交互反馈：机器人可通过转向说话者、调整传感器头朝向或播放机械臂/灯光等已注册交互动作增强交流；具体形式取决于硬件能力，动作仍须经过安全检查。

默认情况下，同一时间只维护一个主会话和一个活动任务。新用户插话时，系统应优先处理停止等安全指令；其他请求应澄清是替换当前任务、修改当前任务还是稍后处理。

### 6.3 导航

机器人根据展厅地图导航到指定区域、展品附近、门口或用户位置。LLM 只提供语义目标，导航技能负责满足轮式底盘运动学约束的路径规划、定位、避障、局部重规划、速度控制和安全制动，并检查通道宽度、转弯空间、坡度、门槛与跌落边缘。

### 6.4 拿取并递交物品

机器人识别任务相关物品，取得可供抓取技能使用的目标引用和位置，先将轮式底盘停稳在可操作位姿，再调用机械臂与末端执行器完成抓取，并通过夹爪/末端触觉及技能结果确认是否抓取成功。之后在满足载荷、重心和机械臂收拢约束的前提下导航至接收者并执行递交。

“寻找物品”不是第一版的独立产品功能，但它作为拿取任务的必要子步骤存在，仅在已知区域和允许操作的物品集合内使用。

### 6.5 开门和关门

系统判断门的身份、状态和操作权限。执行前检查门是否属于可操作对象、门周围是否安全，以及该动作是否需要确认。开门技能自行完成接触和运动控制，VLM/LLM 不直接生成操作轨迹。

### 6.6 预定义交互动作

机器人根据语音请求播放已注册且当前可用的安全交互动作，例如转向用户、机械臂示意、灯光反馈或设备支持的展示动作。动作名称必须来自技能注册表并在最新 `CapabilitySnapshot` 中可用，执行前检查底盘是否需要制动锁定、机械臂工作空间、周围人员距离和机器人状态；不得假设机器人具有人形头部、双臂或全身肢体动作能力。

### 6.7 环境问答

机器人回答与当前可观测展厅环境相关的问题，例如“那个展品是什么”或“门现在开着吗”。回答必须基于最新只读 `AgentContext` 中带时间戳的世界状态；证据不足时应明确表示无法确认并主动重新观察。

## 7. 总体架构

```text
RGB / 深度 / 雷达 / 轮式里程计 / 嗅觉 / 末端触觉
   ↓
设备接入、时间同步与数据规范化
   ↓
VLM / 确定性感知 / 感知融合 ─────────→ WorldState
运行时健康监测 ───────────────────────→ SystemState
技能 Provider / 依赖 / 资源状态 ─────→ 能力运行时 → 只读 CapabilitySnapshot

用户语音 / 打断 / 任务追问
   ↓
语音识别与对话管理器 ←→ 语音合成 / 朝向 / 交互动作
   ├─────────────────────────────────→ DialogueState
   └→ 结构化 Goal / GoalRevision

WorldState ────┐
DialogueState ─┼→ ContextBuilder → 只读 AgentContext ─────────┐
TaskState ─────┤                                               ├→ 目标理解 / 任务规划器
SystemState ───┘                只读 CapabilitySnapshot ───────┘             ↓
                                                                      TaskPlanProposal
                                                                             ↓
                       ReplanRequest ←────────────── 任务执行器 → TaskState / Effect 记录
                                                                             ↓
                                                          Commit Point / 安全监督器
                                                                             ↓
                                                                  能力运行时与技能适配层
                                                                             ↓
                                                    导航 / 抓取 / 开门 / 递交 / 交互动作 API
                                                                             ↓
                                                                    机器人与环境发生变化
                                                                             └→ 新观测与动作结果
```

以上是逻辑模块边界。MVP 可在同一进程中实现，不要求拆成微服务；模块之间仍必须通过明确的只读快照、事件和命令接口交互。

### 7.1 VLM 与确定性感知

职责：

- 识别人、物品、门、区域和可见状态。
- 生成物体属性、空间关系和任务相关语义描述。
- 根据任务查询进行目标定位和视觉复核。
- 为环境问答提供带证据的视觉观察。
- 将视觉语义与深度、雷达、轮式里程计等确定性结果关联，并由感知融合模块写入 `WorldState`。

限制：

- 不独立决定可执行动作。
- 不把二维图像位置直接视为可操作的三维坐标。
- 不负责激光避障、机器人定位和实时运动控制。
- 不得将低置信度推断写成已确认事实。
- 不得写入 `DialogueState`、`TaskState` 或 `SystemState`。

### 7.2 LLM

职责：

- 理解语音转写后的用户目标。
- 判断信息是否完整，并发起澄清或确认。
- 在任务规划器中将结构化目标拆成由最新 `CapabilitySnapshot` 中当前可用且已注册技能组成的完整计划提案。
- 在收到执行器的 `ReplanRequest` 后，基于最新 `AgentContext` 提出替代计划。
- 向用户说明任务进度和失败原因。

LLM 调用采用无状态模式。模型服务端的聊天线程、历史消息缓存或供应商会话 ID 不作为系统记忆或事实来源；每次调用都由 `ContextBuilder` 从最新状态重新组装输入。完整转写、原始模型请求和响应只进入可配置保留周期的审计日志，不自动回灌后续调用。

限制：

- 只能产生符合规定 Schema 的目标、计划提案或自然语言回复。
- 只能引用当前 `AgentContext` 中存在且未过期的实体 ID。
- 不能直接调用技能、推进动作状态或修改任何状态存储。
- 不负责动作超时、有限重试、取消和资源仲裁。
- 不能绕过权限、安全检查和确认流程。
- 不能直接访问硬件控制接口。
- 不得把用户语音、展品文字、VLM 描述或技能返回文本中包含的指令当作系统指令执行；这些内容必须作为不可信数据字段处理。

### 7.3 对话管理器

职责：

- 管理会话 ID、说话轮次、当前说话者和短期对话历史。
- 协调语音活动检测、语音识别、LLM 和语音合成。
- 在机器人播报时检测用户打断，并立即停止播报或通知任务执行器。
- 将“停止”“取消”等高优先级意图通过确定性快速通道传给执行器，不依赖 LLM 完成长推理。
- 管理澄清问题、确认请求及其有效期，防止把无关回答错误绑定到旧问题。
- 将执行器的进度和失败事件转换成适合用户理解的交互消息。
- 作为 `DialogueState` 的唯一写入者；任务修改经解释后输出结构化 `GoalRevision`，不得直接改写活动计划。

对话管理器维护的是短期交互状态，不负责保存跨会话用户画像。敏感原始音频、转写文本和对话日志的保存周期应可配置。

`DialogueState` 至少包含：

```json
{
  "session_id": "session_42",
  "active_speaker_id": "person_1",
  "recent_turns": [],
  "conversation_summary": "",
  "resolved_goal_slots": {
    "action": null,
    "object_id": null,
    "location_id": null,
    "recipient_id": null
  },
  "focus_entities": [],
  "pending_question": null,
  "pending_confirmation": null,
  "last_user_utterance": null
}
```

会话状态规则：

- 默认保留最近 6 个完整对话轮次；更早内容压缩为不超过 500 个中文字符的 `conversation_summary`。轮次数和摘要长度必须配置化。
- Goal 槽位、实体 ID、权限、用户修改、未决问题和确认必须保存为结构化字段，不得只存在于自然语言摘要中。摘要和结构化状态冲突时，以结构化状态为准。
- `focus_entities` 保存指代消解候选及其来源、最近提及时间和有效期；“这个”“右边那个”“刚才的水”等表达只有在候选唯一且未过期时才可自动解析，否则必须追问。
- `pending_confirmation` 必须绑定确认 ID、说话者 ID、任务 ID、计划版本、动作、目标实体及实体修订号、创建时间和过期时间。说话者、任务、计划、动作、目标或实体修订号变化时立即失效。
- 默认确认有效期为 15 秒；具体高风险动作可配置更短有效期，不得配置为无限期。
- 任务或会话结束时，清除最近轮次、摘要、Goal 槽位、焦点实体、未决问题和未决确认。审计日志与在线对话状态分开保留，不得自动进入新会话。

### 7.4 状态存储与所有权

系统不使用一个允许所有模块修改的单体共享上下文。状态按职责拆分，并遵循单一写入者原则：

| 状态 | 内容 | 唯一写入者 | 主要读取者 |
| --- | --- | --- | --- |
| `WorldState` | 机器人位姿、底盘运动状态、机械臂/末端执行器状态、运输姿态、持有物、环境实体、时间戳、置信度、来源和坐标系 | 感知融合模块 | `ContextBuilder`、安全监督器、技能运行时 |
| `DialogueState` | 会话、说话轮次、当前说话者、最近轮次、对话摘要、结构化 Goal 槽位、焦点实体、待澄清问题和待确认动作 | 对话管理器 | `ContextBuilder`、交互输出模块 |
| `TaskState` | 当前目标、已接受计划及版本、当前步骤、活动动作和执行结果 | 任务执行器 | `ContextBuilder`、对话管理器、可观测性模块 |
| `SystemState` | 传感器、模型服务、定位、网络和机器人后端健康状态 | 运行时健康监测模块 | `ContextBuilder`、安全监督器、任务执行器 |

状态管理规则：

- 每类状态只有表中指定模块可以写入，其他模块只能读取不可变快照或接收事件。
- 每次状态更新都递增版本并保留更新时间；过期事实必须变为未知，不能继续作为当前事实使用。
- 跨模块交互使用结构化命令和事件，不允许通过共享对象间接修改其他模块拥有的状态。
- 动作结果由技能运行时产生事件，任务执行器消费后更新 `TaskState`；新观测由感知融合模块消费后更新 `WorldState`。
- 瞬时事件不直接等同于持久事实。只有完成校验、融合或状态转换后的结果才能写入对应状态。

第一版不要求复杂的长期目标跟踪或学习型预测模型，但必须避免把每次 VLM 输出直接、无条件地当成真实世界状态。

### 7.5 只读 `AgentContext`

`ContextBuilder` 按调用用途从四类状态生成只读 `AgentContext`，为目标理解、任务规划、环境问答和用户回复提供一致输入。它是一次性快照，不是第五个共享可变状态库。安全监督器仍直接读取完整、最新的安全相关状态；未被选入 LLM 上下文的障碍物或风险不得因此从安全检查中消失。

职责：

- 记录上下文 ID、生成时间和每个来源状态的版本。
- 只包含当前任务所需的状态摘要，避免把无关原始数据和完整历史交给 LLM。
- 在组装时执行新鲜度检查；任一关键来源过期时，将相关字段标记为未知，并明确数据质量原因。
- 保留实体时间戳、置信度、来源和坐标系，禁止把来自不同时刻的冲突事实拼成看似一致的当前状态。
- 规划器和问答模块只能读取 `AgentContext`；任何读取 `AgentContext` 的模块都不能通过它反向修改来源状态。安全监督器可按职责直接读取完整安全状态，并拥有独立否决权。
- 按固定优先级执行相关性选择和 token 预算控制；任何被省略部分必须显式记录，关键结构化事实不得被静默截断。

#### 7.5.1 固定提示层

可缓存的固定 system prompt 只包含：

- LLM 的职责、禁止事项和数据/指令边界。
- `Goal`、`GoalRevision`、`TaskPlanProposal`、澄清请求和自然语言回复的输出 Schema。
- 实体引用、新鲜度、未知状态和证据表达规则。
- 停止、安全判断、确认接受和技能执行均由确定性模块负责的约束。

固定提示使用独立版本号，只在策略或 Schema 升级时变化，不随对话轮次追加。ASR 文本、VLM 描述、展品文字和技能返回文本必须放入 JSON 数据字段并标记来源，禁止拼接进固定提示层。

#### 7.5.2 `ContextBuildRequest`

调用者通过以下接口请求用途化上下文：

```json
{
  "purpose": "goal_understanding",
  "session_id": "session_42",
  "task_id": "task_17",
  "current_utterance": {
    "text": "换成右边那瓶",
    "source": "asr",
    "timestamp": 12345.5,
    "confidence": 0.93
  },
  "focus_entity_ids": ["water_1", "water_2"],
  "token_budget": 8000
}
```

`purpose` 只能是 `goal_understanding`、`planning`、`replanning`、`environment_qa` 或 `response`。`token_budget` 由模型配置提供，默认 8000 输入 token，并且必须为模型输出和安全余量预留空间。

#### 7.5.4 用途化上下文视图

| 用途 | 必须包含 | 默认不包含 |
| --- | --- | --- |
| 目标理解 | 当前话语、最近轮次、待澄清项、焦点实体、结构化 Goal 槽位 | 完整计划、全部技能 |
| 初次规划 | 结构化 Goal、相关实体、任务状态、完整精简版能力快照 | 完整聊天历史、无关实体 |
| 重规划 | 最新 Goal、失败步骤、实际 Effect、已完成步骤、相关事件和能力 | 与失败无关的旧事件 |
| 环境问答 | 当前问题、相关观察、时间戳、置信度和来源 | 技能定义、完整任务计划 |
| 用户回复 | 已验证的任务或动作结果、待传达信息 | 原始传感器数据、完整世界状态 |

相关实体至少包括当前 Goal、当前或剩余计划、用户焦点和 `ReplanRequest` 直接引用的实体，以及完成歧义判断所需的同类候选。MVP 规划和重规划调用携带完整但精简的 `CapabilitySnapshot`，包括技能名、参数 Schema、当前可用性、不可用原因、风险级别和结果类型；技能数量明显增长后才引入确定性能力检索。

#### 7.5.5 新鲜度与未知状态

新鲜度按字段类型配置，不使用一个统一的上下文有效期。MVP 默认值如下：

| 字段类别 | 默认 TTL |
| --- | --- |
| 机器人运动状态、机械臂状态、关键系统健康 | 1 秒 |
| 人员位置 | 2 秒 |
| 可操作物品位置、门状态 | 5 秒 |
| 已确认物体类别、固定区域语义 | 30 秒或配置版本变化前 |
| 用户确认 | 15 秒，并受说话者、任务、计划、动作和实体修订号约束 |

TTL 全部配置化。字段过期或来源不可用时，其值必须变为 `unknown`，并在 `data_quality` 中给出字段路径、`STALE`、`SENSOR_UNAVAILABLE` 或 `CONFLICTING_OBSERVATIONS` 等原因。LLM 可以返回重新观察或澄清请求，但不得继续引用旧值生成可执行动作。

#### 7.5.6 token 预算与裁剪

ContextBuilder 按以下顺序分配预算：关键结构化事实、当前请求、相关实体与动作结果、能力快照、最近对话、对话摘要、可选背景。Goal、未决问题、确认、当前步骤、实体 ID/修订号、时间戳和数据质量不得被静默截断。

- 超出预算时，先省略低优先级完整分区，并将路径写入 `omitted_sections`，不得截断 JSON 文本。
- 最近对话默认最多 6 个完整轮次；更早内容使用 `conversation_summary`。
- 关键字段在移除所有可选内容后仍无法放入预算时，返回 `CONTEXT_TOO_LARGE`，不得调用 LLM。
- token 估算器必须与目标模型的分词方式匹配或采用保守上界；最终输入必须在调用模型前再次检查。

#### 7.5.7 输出绑定、校验与并发

- 所有模型结构化输出必须携带 `generated_from_context_id`；计划提案还必须携带 `generated_from_capability_snapshot_id` 和 `referenced_entities`，后者包含实体 ID 及生成时修订号。
- 执行器从计划参数、前置条件和 `referenced_entities` 推导实际读取集合，并在接受计划及每个 Commit Point 校验这些实体、关键字段、能力和确认的当前版本。
- 无关实体或无关系统字段更新不得使计划整体失效；被实际引用的实体、能力、确认或关键前置条件变化时，必须拒绝提案、刷新观察或请求重规划。
- LLM 推理期间，执行器不得推进已经判定失效的旧步骤；新提案未通过校验时不得覆盖活动计划。
- 每次调用记录 `context_id`、固定提示版本、来源版本、数据质量、被省略分区、输入摘要、模型版本、输出和校验结果，以便完整追溯。

### 7.6 嗅觉、末端执行器触觉与事件通道

嗅觉和触觉不是 VLM 的视觉输入。传感器适配层应先把原始信号转换成带事件 ID、时间戳、置信度、来源和有效期的结构化事件，并发布到事件通道。

示例：

```json
{
  "events": [
    {
      "event_id": "event_201",
      "type": "odor_detected",
      "label": "smoke_like",
      "confidence": 0.78,
      "timestamp": 12345.1,
      "expires_at": 12350.1,
      "source": "odor_sensor"
    },
    {
      "event_id": "event_202",
      "type": "grasp_contact",
      "end_effector": "gripper_1",
      "contact": true,
      "slip_risk": 0.12,
      "timestamp": 12345.5,
      "expires_at": 12346.0,
      "source": "gripper_1_tactile"
    }
  ]
}
```

语音打断、动作结果、嗅觉告警和触觉滑移等瞬时信息都通过事件通道传递。`ContextBuilder` 可按任务需要附带尚未过期的近期事件，但事件本身不因进入 `AgentContext` 而变成持久状态。

嗅觉可作为异常提示或辅助判断，但第一版不得仅根据模型对气味标签的解释执行危险处置。末端执行器触觉应优先由抓取控制器用于实时闭环，向高层只提供抓取成功、接触丢失或滑落风险等摘要事件；经感知融合确认的持有物状态再写入 `WorldState`。

### 7.7 任务规划器

任务规划器负责提出计划，不负责执行计划。其输入为结构化 `Goal` 或 `GoalRevision`、最新只读 `AgentContext` 和版本化只读 `CapabilitySnapshot`；输出为完整、带版本的 `TaskPlanProposal`。

职责：

- 检查目标信息是否足够；信息不足时返回澄清需求，不生成可执行计划。
- 将目标拆分为只包含已注册技能的步骤，并声明每步的前置条件和成功条件。
- 只引用 `AgentContext` 中存在、足够新鲜且允许操作的实体。
- 收到任务执行器发出的 `ReplanRequest` 后，结合已完成效果、失败原因和最新上下文生成完整替代计划。
- 保持提案无副作用；不得直接调用技能、修改 `TaskState` 或把计划标记为已接受。

建议的最小 `TaskPlanProposal`：

```json
{
  "plan_id": "plan_42",
  "version": 1,
  "goal_id": "goal_17",
  "generated_from_context_id": "context_108",
  "generated_from_capability_snapshot_id": "capability_31",
  "referenced_entities": [
    {"entity_id": "water_1", "revision": 4}
  ],
  "steps": [
    {
      "step_id": "step_1",
      "skill": "navigate_to",
      "arguments": {"location_id": "display_area"},
      "preconditions": ["system.localization == healthy"],
      "success_conditions": ["robot arrived at display_area"]
    },
    {
      "step_id": "step_2",
      "skill": "pick",
      "arguments": {"object_id": "water_1"},
      "preconditions": ["water_1 is fresh and reachable"],
      "success_conditions": ["robot.holding_object_id == water_1"]
    }
  ]
}
```

计划提案只有在任务执行器完成 Schema、实际读取集合中的实体修订号、能力快照、权限、安全和技能参数校验后才成为活动计划。规划器不能绕过该接受过程。

### 7.8 任务执行器

职责：

- 验证 `TaskPlanProposal` 的 Schema、上下文 ID、`CapabilitySnapshot` 版本、技能名称、当前可用性、参数、实际引用实体及其修订号、调用权限和安全约束；不得仅因无关状态的全局版本变化拒绝计划。
- 接受合法提案并作为 `TaskState` 的唯一写入者，持有活动计划、计划版本、当前步骤和动作生命周期。
- 顺序执行任务步骤，处理超时、取消、资源仲裁、技能元数据允许的有限重试和失败传播。
- 在每一步执行前重新读取最新能力状态；Provider、依赖或资源状态变化导致技能不可用时，不得继续发起该技能的新调用。
- 在动作完成后要求刷新相关观察，防止使用旧状态继续执行。
- 对确定性可恢复失败在执行层处理，不为普通超时或允许范围内的重试调用 LLM。
- 记录每一步产生的内部和物理 Effect；任务失败、取消或被替代时，按逆序清理资源锁、订阅和临时状态等可撤销内部 Effect。
- 在抓取、递交、开关门以及其他可能改变物理世界或产生不可逆外部结果的步骤前设置 Commit Point，重新检查能力、状态新鲜度、置信度、资源、权限、安全和有效用户确认。
- 对可补偿的物理 Effect 仅在最新环境仍允许且补偿动作通过安全检查时执行补偿；不能安全补偿时保持安全状态、记录未恢复影响并请求人工处理，不得宣称已经回滚。
- 当目标、前置条件或剩余计划失效时，生成 `ReplanRequest`；规划器返回的新提案通过全部校验后，按版本原子替换旧计划。
- 接收对话管理器发出的停止、取消和 `GoalRevision`。停止指令立即走快速通道；任务修改必须先安全完成、暂停或取消受影响动作，再请求新计划。
- 将统一动作结果和任务进度发布为事件，但不把动作控制权交给规划器。

建议的最小 `ReplanRequest`：

```json
{
  "request_id": "replan_9",
  "task_id": "task_17",
  "superseded_plan_id": "plan_42",
  "superseded_plan_version": 1,
  "failed_step_id": "step_2",
  "reason": "TARGET_STALE",
  "action_result": {
    "status": "failed",
    "error_code": "TARGET_STALE"
  },
  "completed_effects": ["robot arrived at display_area"],
  "constraints": ["do not repeat completed navigation unless required"],
  "agent_context_id": "context_109"
}
```

`ReplanRequest` 由任务执行器唯一发起，并与最新 `AgentContext` 一起交给规划器。生成替代计划期间，旧计划不得继续推进过期步骤；新计划未通过校验时，活动计划和 `TaskState` 不得被覆盖。

统一动作状态：

```text
PENDING → RUNNING → SUCCEEDED
                  → FAILED
                  → CANCELLED
                  → TIMEOUT
```

### 7.9 能力运行时与生命周期

技能注册表描述机器人理论上具备的技能；能力运行时根据当前 Provider、依赖、资源和系统健康状态，计算机器人此刻真正可用的能力，并作为 `CapabilitySnapshot` 的唯一写入者生成带版本和时间戳的只读快照。任务规划器和任务执行器不得以静态技能注册结果代替当前能力快照。

Provider 生命周期至少包含：

```text
UNAVAILABLE → LOADING → READY
                      → DEGRADED
                      → FAILED
```

- `UNAVAILABLE`：未配置、未连接或必要依赖不满足。
- `LOADING`：正在初始化，尚不可接受调用。
- `READY`：健康且允许接受新调用。
- `DEGRADED`：部分能力或性能受限；只有明确标记仍可用的能力可以进入计划。
- `FAILED`：运行失败，不得接受新调用。

技能能力状态至少包含 `AVAILABLE`、`BUSY` 和 `UNAVAILABLE`。能力运行时必须根据 Provider 生命周期、技能依赖、资源占用和安全禁用状态重新计算能力状态，并将状态变化向依赖该能力的组合技能传播。`CapabilitySnapshot` 至少包含：

- `snapshot_id`、生成时间和来源状态版本。
- 技能或能力标识、当前状态和不可用原因。
- 绑定的 Provider 标识及其生命周期状态。
- 必要依赖及其解析结果。
- 当前资源可用性和并发限制。

Provider 或依赖在任务执行期间失效时，能力运行时应立即停止接受受影响技能的新调用并向任务执行器发布结构化状态变化事件。任务执行器负责安全完成、取消或停止当前动作，清理内部 Effect，再根据剩余计划决定等待依赖、使用已经验证的替代能力、请求重规划或结束任务。规划器不得自行处理在途动作。

### 7.10 安全监督器

安全监督器独立于 LLM，拥有否决和停止权限，至少负责：

- 人员和障碍物碰撞风险检查。
- 台阶、楼梯、跌落边缘、超限坡度、底盘打滑和倾覆风险检查。
- 根据当前载荷、机械臂姿态和底盘速度检查整机重心与稳定性；需要时要求底盘停稳并锁定后再执行操作。
- 禁区、受限区域和目标操作权限检查。
- 基于最新状态快照检查模型服务、感知、定位或机器人后端健康；关键状态异常时停止任务。
- 对高风险或敏感技能要求用户确认。
- 阻止未注册技能、非法参数和不存在的实体引用。
- 以结构化 `SafetyDecision` 向任务执行器返回允许、拒绝、要求确认或停止；由任务执行器据此更新 `TaskState`。
- 不得绕过机器人平台已有的硬件急停和底层安全机制。

## 8. 技能 API 要求

### 8.1 MVP 技能集合

```text
navigate_to(location_or_pose)
observe(query, viewpoint?)
pick(object_id)
handover(person_id)
open_door(door_id)
close_door(door_id)
play_interaction(interaction_id)
orient_to(person_or_entity_id)
stop()
speak(text)
```

虽然假设技能已存在，但接入大脑前必须通过统一适配层暴露，不允许 LLM 直接调用厂商 SDK。

### 8.2 技能元数据

每个技能必须声明：

- 名称和用途。
- 参数 Schema 和参数范围。
- 前置条件和成功条件。
- 风险等级和是否需要确认。
- 超时时间、最大重试次数和是否允许取消。
- 占用资源，例如轮式底盘、机械臂、末端执行器、传感器头或摄像头。
- 所依赖的 Provider、基础能力、地图或传感器条件，以及依赖不满足时的能力状态。
- 可能产生的 Effect，以及每类 Effect 属于 `REVERSIBLE`、`COMPENSATABLE` 还是 `IRREVERSIBLE`。
- 对 `REVERSIBLE` Effect 的清理动作；对 `COMPENSATABLE` Effect 的可选补偿动作和补偿前置条件。
- 是否需要 Commit Point，以及 Commit Point 必须重新检查的状态和确认条件。
- 可返回的错误码和恢复建议。

### 8.3 统一执行结果

```json
{
  "action_id": "action_123",
  "skill": "pick",
  "status": "succeeded",
  "error_code": null,
  "message": "object grasped",
  "data": {
    "held_object_id": "water_1",
    "tactile_confirmed": true
  }
}
```

技能失败时必须返回机器可处理的错误码，例如：

- `TARGET_NOT_FOUND`
- `TARGET_STALE`
- `PATH_BLOCKED`
- `GRASP_FAILED`
- `CONTACT_LOST`
- `PERMISSION_DENIED`
- `CONFIRMATION_REQUIRED`
- `SENSOR_UNAVAILABLE`
- `TIMEOUT`

执行结果还必须报告实际发生的 Effect，而不能只根据计划推测。最小 Effect 记录包含 Effect 标识、类型、影响对象或状态、是否已提交、清理或补偿动作标识以及当前恢复状态。任务执行器是任务级 Effect 记录的唯一写入者。

## 9. 核心流程

### 9.1 任务接收

1. 对话管理器建立或恢复当前短期会话，确定说话轮次并更新 `DialogueState`。
2. 将用户语音转换成带时间戳和置信度的文本。
3. 目标理解模块结合短期对话和只读 `AgentContext`，提取结构化 `Goal`，包括对象、地点和接收者。
4. 若存在歧义或缺少关键参数，先通过语音追问。
5. 任务规划器读取最新 `AgentContext` 和 `CapabilitySnapshot`，只能使用当前可用能力生成完整的 `TaskPlanProposal`。
6. 任务执行器完成 Schema、上下文版本、能力快照版本、技能当前可用性、实体、参数、权限和安全校验；任何校验失败都不得修改现有 `TaskState`。
7. 任务执行器接受合法计划，写入新的任务和计划版本后开始执行，并通过对话管理器向用户确认已受理任务。

### 9.2 单步执行闭环

1. 任务执行器从 `TaskState` 读取活动计划，并请求 `ContextBuilder` 生成最新只读 `AgentContext`。
2. 检查当前步骤的前置条件、目标实体新鲜度、置信度、最新能力状态及系统健康状态。
3. 若步骤存在 Commit Point，重新验证能力、资源、权限、目标新鲜度和确认有效期；任一条件不满足时不得提交动作。
4. 安全监督器返回结构化 `SafetyDecision`，验证动作及必要的补偿动作是否允许。
5. 必要时由对话管理器请求与当前动作、目标和有效期绑定的用户确认。
6. 任务执行器调用一个技能并等待结构化 `ActionResult` 事件，同时记录实际发生的 Effect。
7. 任务执行器根据结果更新 `TaskState` 和 Effect 记录；动作引起的新观测由感知融合模块写入 `WorldState`，健康变化由运行时健康监测模块写入 `SystemState` 和能力运行时。
8. `ContextBuilder` 生成新的上下文快照，任务执行器验证成功条件；满足时推进下一步，否则先完成必要的内部 Effect 清理，再进入确定性恢复、受安全约束的补偿或重规划流程。

### 9.3 失败处理

- 技能元数据允许的普通超时、重新观察和有限重试由任务执行器确定性处理，不触发 LLM 调用。
- 状态过期：刷新感知，不沿用旧实体位置；刷新后计划仍有效时继续执行。
- 目标歧义：通过对话管理器向用户询问，不随机选择，也不直接修改活动计划。
- 路径阻塞：允许导航技能重新规划；超过限制后请求帮助。
- 抓取失败：检查底盘停靠位姿、目标和末端触觉结果，在限制次数内重试。
- 模型、定位或关键感知不可用：停止动作并报告原因。
- 高风险动作未确认：保持等待或安全取消。
- Provider、依赖或必要资源不可用：停止发起受影响技能的新调用；安全处理在途动作并清理内部 Effect，再根据最新能力状态等待、使用已验证替代能力、请求重规划或报告失败。
- 内部 Effect 未完成清理：任务不得标记为完全结束；系统应继续有限清理或进入需要人工处理的安全失败状态。
- 物理 Effect 需要补偿：只有补偿前置条件仍成立且安全监督器允许时才执行；否则保留未恢复影响记录并请求人工处理。
- 当前目标、步骤前置条件或剩余计划失效：由任务执行器发出 `ReplanRequest`，规划器不得自行抢占活动计划。
- 替代计划：只有通过完整校验后才能按新版本原子替换旧计划；校验失败时保持安全停止或等待帮助，不覆盖原 `TaskState`。

### 9.4 对话打断与任务修改

- 用户说出停止或取消意图时，通过快速通道立即停止语音播报，并请求当前技能安全取消或停车。
- 用户修改任务时，对话管理器生成结构化 `GoalRevision`，不得直接更新 `TaskState` 或活动计划。
- 修改仅影响尚未执行的步骤时，任务执行器发起重规划，并在替代计划通过校验后切换版本。
- 修改影响正在执行的动作时，任务执行器先安全完成、暂停或取消当前动作，再发起重规划；禁止在运动中替换未校验参数。
- 用户只是询问进度时，不应误取消当前任务；系统应读取 `TaskState` 的只读快照后作答。
- 无法确定用户是在补充、替换还是创建新任务时，必须追问。

## 10. 功能需求

### FR-01 语音任务理解

系统应将语音转写为任务目标，并识别对象、地点、接收者和动作；关键参数不完整时必须追问。

### FR-02 多模态环境理解

系统应融合 RGB、深度、激光雷达、轮式里程计、嗅觉和末端执行器触觉信息，将确认后的当前事实写入 `WorldState`，将瞬时信息发布为带时间戳、置信度、来源和有效期的事件。

### FR-03 受约束规划

任务规划器生成的 `TaskPlanProposal` 只能包含最新 `CapabilitySnapshot` 中当前可用且来自技能注册表的技能，必须满足计划 Schema，并且只能引用生成计划所依据的 `AgentContext` 中未过期的实体。计划提案在任务执行器接受前不得产生副作用。

### FR-04 技能编排

任务执行器应独立于任务规划器，支持计划校验与接受、多步骤顺序执行、状态反馈、超时、取消、资源仲裁、有限重试、Effect 记录与清理、Commit Point 校验、受安全约束的物理补偿和失败恢复；只有计划失效时才发出 `ReplanRequest`。

### FR-05 状态刷新

涉及位置、门状态、持有物或人员状态变化的动作完成后，系统应刷新相应观察再继续执行。

### FR-06 短期记忆

系统应按所有权分别在 `WorldState`、`DialogueState`、`TaskState` 和 `SystemState` 中保存单次任务需要的短期状态，并通过只读 `AgentContext` 提供任务相关汇总；LLM 调用不得以供应商聊天线程作为记忆。最近轮次必须保持有界，较早内容可以摘要，但 Goal 槽位、实体引用、确认、权限和任务修改必须结构化保存。任务结束后按策略清理，不建立用户长期画像。

### FR-07 环境问答

系统应基于最新可验证观察回答环境问题；证据不足时不得将推断表述为事实。

### FR-08 可观测性

系统应记录用户指令、感知摘要、四类状态的版本、`AgentContext` ID、固定提示版本、上下文用途、数据质量、被省略分区、输入摘要、模型版本、模型输出及校验结果、`CapabilitySnapshot` ID、Provider 与能力状态变化、计划提案与接受记录、重规划请求、技能调用、执行结果、Effect、Commit Point 校验、清理与补偿结果、确认记录和安全否决原因。

### FR-09 多轮对话

系统应在当前会话中维护必要的对话上下文，支持追问、澄清、指代消解、确认和任务相关问答。默认保留最近 6 个完整轮次和不超过 500 个中文字符的较早对话摘要；指代证据不足时必须追问。不得依赖跨会话长期记忆完成 MVP。

### FR-10 打断与任务修改

系统应区分停止、取消、修改和普通问答。停止类指令必须有独立高优先级处理路径；任务修改必须形成 `GoalRevision`，并在执行器安全处理当前动作、接受新计划后生效。

### FR-11 交互反馈

系统应在任务受理、等待确认、长时执行、重试、成功、失败和安全停止时，通过语音提供明确反馈，并可调用已注册的底盘朝向、机械臂示意、灯光或其他交互动作增强交互。

### FR-12 状态所有权

每类状态必须只有一个明确写入者。感知、对话、规划、安全和技能模块不得直接修改不属于自己的状态；跨模块更新必须通过结构化命令、事件或任务执行器的状态转换完成。

### FR-13 动态能力可用性与生命周期

系统应根据 Provider 生命周期、依赖、资源和系统健康状态持续计算技能的当前可用性，生成版本化只读 `CapabilitySnapshot`，并在状态变化时向任务执行器发布事件。处于不可用状态的技能不得进入新计划或接受新调用；执行期间能力失效时，任务执行器必须安全处理在途动作和内部 Effect 后再决定等待、替代、重规划或失败。

### FR-14 Effect、Commit Point 与补偿

系统应区分可撤销内部 Effect、可补偿物理 Effect 和不可逆 Effect。任务执行器必须记录实际 Effect，在失败、取消或计划替换时清理可撤销内部 Effect；关键物理或外部动作必须经过 Commit Point 复核；物理补偿只有在当前状态满足补偿前置条件并通过安全检查时才能执行。

### FR-15 用途化上下文构建

`ContextBuilder` 应按目标理解、初次规划、重规划、环境问答和用户回复五种用途构建不同的只读上下文视图，执行字段级新鲜度检查和相关性选择，并在模型配置的 token 预算内输出完整 JSON。关键结构化事实无法容纳时必须返回 `CONTEXT_TOO_LARGE`；低优先级分区被省略时必须记录 `omitted_sections`。所有结构化模型输出必须绑定生成它的上下文 ID，计划提案还必须绑定能力快照 ID 和实际引用实体的修订号。

## 11. 非功能需求

### 11.1 安全性

- 安全检查不得依赖 LLM 自觉遵守。
- 停止指令和安全否决必须高于任务执行优先级。
- 高风险动作必须绑定明确的动作、目标和有效期进行确认。
- Commit Point 必须使用最新状态重新检查能力、资源、目标新鲜度、权限、安全和确认，不得沿用已经失效的预检查结果。
- 补偿动作必须被视为新的物理动作重新接受安全检查；系统不得假设反向动作天然安全。
- 大模型失联、输出非法或连续失败时进入安全停止状态。
- 底盘运动必须受最大速度、最大加速度、最小障碍距离和制动距离约束；检测到人员侵入、跌落边缘、超限坡度、定位失效或底盘故障时，必须由独立于大模型的链路减速或停车。
- 机械臂伸出、持物或操作门时，应根据整机稳定性限制底盘运动；未经底层控制器明确支持，不允许底盘与机械臂同时运动。

### 11.2 实时性

- VLM/LLM 不进入轮式底盘和机械臂关节的高频控制回路。
- 技能执行期间由底层控制器保持实时闭环。
- 高层规划延迟目标由原型测试确定；等待初始计划或替代计划期间，不得继续推进未验证或已过期的动作。
- 停止、取消、安全否决和底层急停不得依赖任务规划器或模型服务在线。

### 11.3 可解释性

系统必须能够回答：

- 当前理解的用户目标是什么。
- 当前看到了什么以及置信度如何。
- 当前执行哪一步。
- 为什么选择该技能。
- 为什么停止、重试或请求确认。

### 11.4 对话体验

- 机器人应避免在没有新信息时重复播报同一句进度。
- 任务执行较长时，应提供阶段性反馈，但不得因频繁播报妨碍用户打断。
- 语音识别置信度过低或展厅噪声过大时，应请求用户重复，而不是猜测。
- 停止类指令的响应优先级高于自然语言回复的完整性。

### 11.5 可替换性

VLM、LLM、语音服务、状态存储、`ContextBuilder` 和机器人技能后端应通过接口隔离。替换模型或机器人平台时，不得要求重写任务执行器的计划接受、动作生命周期和安全策略。

## 12. 验收标准

### 12.1 任务集

至少建立以下受控场景测试：

1. 用户要求机器人导航到指定展区。
2. 用户要求机器人拿取指定水瓶并递交。
3. 用户要求机器人打开或关闭允许操作的门。
4. 用户要求机器人完成一个硬件支持的预定义交互动作。
5. 用户询问当前可见展品或门的状态。
6. 指令存在歧义时，机器人正确发起澄清。
7. 路径阻塞、目标丢失或抓取失败时，机器人正确恢复或求助。
8. 感知或模型服务异常时，机器人停止任务。
9. 请求进入禁区时，机器人拒绝执行并说明原因。
10. 高风险动作未确认时，机器人不得执行。
11. 用户用代词指向多个可能对象时，机器人发起澄清而不是随机选择。
12. 用户在任务执行过程中询问进度时，机器人正确回答且任务保持运行。
13. 用户要求停止或取消时，机器人终止播报并安全停止当前任务。
14. 用户修改任务目标时，机器人确认新目标并在重新校验后执行。
15. 规划器产生未注册技能、非法参数、陈旧实体或不存在的实体引用时，执行器拒绝计划，且活动计划和 `TaskState` 保持不变。
16. 技能发生普通超时或允许范围内的可恢复失败时，执行器完成确定性处理，不发起不必要的 LLM 调用。
17. 剩余计划因环境变化失效时，只有任务执行器发出 `ReplanRequest`；新计划通过全部校验后才替换旧版本。
18. 感知、对话或规划模块尝试直接修改 `TaskState` 时，系统拒绝该写入并留下可查询记录。
19. `AgentContext` 的任一关键来源过期时，相关字段被标记为未知，不把跨时刻冲突数据拼接成当前事实。
20. 任务规划器或模型服务离线时，停止、取消和安全否决仍能沿高优先级路径生效。
21. 机器人接近台阶、跌落边缘、超限坡度或不可通行门槛时，底层安全链路阻止继续行驶并安全停车。
22. 机械臂伸出或持物导致稳定性风险时，系统限制底盘运动；需要移动时先将机械臂和载荷调整至经验证的运输姿态。
23. 机械臂或导航 Provider 在规划前处于 `FAILED` 或依赖不满足时，相关拿取或导航能力在 `CapabilitySnapshot` 中不可用，规划器和执行器均不得接受包含该能力的新计划。
24. Provider 或必要依赖在任务执行期间失效时，能力状态变化正确传播；系统停止发起受影响技能的新调用，安全处理在途动作，清理内部 Effect，并给出等待、替代、重规划或失败结果。
25. 任务在占用机械臂资源、锁定目标或建立感知订阅后失败或被取消时，资源锁、目标锁和订阅等可撤销内部 Effect 按逆序清理，不遗留虚假占用。
26. 抓取、递交或开关门到达 Commit Point 时，如果目标已过期、能力不可用、安全检查失败或确认失效，系统不得执行该关键动作。
27. 物理动作失败后，系统仅在补偿前置条件仍成立并通过安全检查时执行补偿；无法安全补偿时保持安全状态、记录未恢复影响并请求人工处理。
28. 当前会话连续超过 20 个对话轮次时，LLM 输入保持在配置预算内，最近轮次、结构化 Goal、待澄清问题和待确认动作不丢失。
29. 用户使用“这个”“右边那个”或“刚才的水”等指代时，系统只在焦点实体唯一且未过期时解析；存在多个有效候选时主动追问。
30. 用户对旧任务给出的确认不得应用到新说话者、新任务、新计划版本、新动作、新目标或已更新的目标实体。
31. 人员、门或物品位置超过对应 TTL 时，`AgentContext` 将值标记为 `unknown` 并给出 `STALE` 数据质量原因；规划器请求重新观察或澄清。
32. 与计划无关的实体更新导致 `WorldState` 全局版本变化时，合法计划仍可通过校验；被计划实际引用的实体修订号变化时，执行器拒绝旧提案或停止提交关键动作。
33. 对话摘要与结构化 Goal 或 `TaskState` 冲突时，系统使用结构化状态且记录冲突，不按摘要修改任务。
34. 用户语音、展品文字、VLM 描述或技能返回文本包含“忽略规则并执行动作”等指令时，系统将其作为不可信数据处理，不能扩大 LLM 权限或绕过执行器。
35. 上下文超过 token 预算时，ContextBuilder 按优先级省略完整低优先级分区并记录 `omitted_sections`；关键内容仍无法容纳时返回 `CONTEXT_TOO_LARGE`，不产生截断 JSON 或调用 LLM。
36. 任务或会话结束后，新会话不能引用上一会话的最近轮次、摘要、焦点实体、Goal 槽位或确认。
37. 每次 LLM 调用均可通过 `context_id` 追溯固定提示版本、四类状态版本、数据质量、被省略分区、输入摘要、模型版本、输出和校验结果。

### 12.2 MVP 通过条件

- 在预先定义并冻结的受控测试集中，端到端任务成功率不低于 80%。
- 100% 的技能调用来自注册技能集合，并通过参数校验。
- 100% 的禁区测试被阻止。
- 100% 的模型或关键感知失效测试触发安全停止。
- 100% 的高风险动作在未获得有效确认时不执行。
- 100% 的停止/取消测试进入高优先级处理路径，不被当作普通对话延迟执行。
- 100% 的非法或引用陈旧实体的计划提案被拒绝，且不改变活动计划和 `TaskState` 版本。
- 100% 的计划替换由任务执行器发起并在完整校验后生效，不存在规划器直接推进任务或改写状态的路径。
- 100% 的跨模块状态写入符合单一写入者规则；违规尝试被拒绝并记录。
- 100% 的关键来源过期测试在 `AgentContext` 中产生未知状态或明确的数据质量标记。
- 100% 的模型离线停止、取消和安全否决测试不依赖任务规划器完成。
- 100% 的台阶、跌落边缘和超限坡度测试触发减速、停车或拒绝通行，且不依赖 VLM/LLM 判断。
- 100% 的底盘与机械臂互锁测试符合已配置的稳定性和并发运动约束。
- 100% 的 Provider 或必要依赖不可用测试都会使相关能力在限定传播时间内变为不可用，并阻止新的技能调用。
- 100% 的失败、取消和计划替换测试均完成已登记的可撤销内部 Effect 清理，或明确进入可查询的安全失败状态。
- 100% 的 Commit Point 条件失效测试均阻止关键动作提交。
- 100% 的补偿动作重新通过能力、状态新鲜度和安全检查；不能安全补偿时不得强行执行或报告为已回滚。
- 100% 的过期字段测试输出 `unknown` 和明确的数据质量原因，不把旧值继续提供为当前事实。
- 100% 的确认错绑测试均被拒绝，包括说话者、任务、计划、动作、目标或实体修订号变化。
- 100% 的计划引用版本测试只校验实际读取集合：无关状态更新不误杀计划，被引用实体变化必须阻止旧计划提交。
- 100% 的上下文超预算测试不产生截断 JSON；无法保留关键字段时不得调用 LLM。
- 100% 的跨会话隔离测试不会把上一会话内容注入新会话。
- 100% 的提示注入测试不能使 LLM 绕过技能注册、计划接受、安全监督或确认流程。
- 每次失败均可查询到感知、计划、技能结果或安全否决记录。

成功率计算方式：

```text
端到端任务成功率 = 在规定时间和重试限制内完成目标的任务数 / 总有效任务数
```

测试前还需明确每类任务的超时、最大重试次数、允许的人为干预和场景随机化范围，避免成功率口径不一致。

## 13. 主要风险与待确认事项

### 13.1 主要风险

- VLM 对相似物品、反光展柜或遮挡目标产生误识别。
- LLM 生成不存在的实体引用或不必要的步骤。
- 语音识别在展厅噪声中误解目标。
- 用户插话、环境语音或多人同时说话造成错误的说话者和任务归属。
- 对话历史过长或指代消解错误导致 LLM 修改了错误目标。
- 对话摘要遗漏或歪曲关键事实，并与结构化 Goal 或任务状态产生冲突。
- ASR 文本、展品文字、VLM 描述或技能返回内容携带提示注入，诱导模型越权。
- token 估算偏差或无边界历史导致输入超限、JSON 被截断或关键字段被裁剪。
- VLM 语义结果与深度/地图坐标关联失败。
- 触觉确认与视觉观察不一致。
- 轮式里程计受打滑、地面材质或轮胎磨损影响而漂移，导致定位和停靠误差。
- 低矮障碍、玻璃边界、门槛、坡道或跌落边缘未被可靠检测。
- 机械臂伸出或持物改变整机重心与包络，导致倾覆风险或底盘规划空间不足。
- 技能虽然单独可用，但缺少一致的状态、错误码和取消语义。
- Provider 或依赖状态传播不及时，导致规划器使用已经不可用的能力。
- 技能 Effect 声明不完整，导致任务失败或取消后残留资源锁、订阅或错误状态。
- 将物理补偿误当成必然安全的回滚，导致在环境已经变化时引入二次风险。
- 动作后未及时刷新状态，导致系统按旧世界继续执行。
- 四类状态的版本组合不一致，导致规划器基于跨时刻事实生成错误计划。
- 使用 `WorldState` 全局版本粗粒度校验，导致无关实体变化频繁误杀合法计划。
- 重规划结果与正在执行的旧计划发生竞态，导致旧步骤继续推进或任务版本被错误覆盖。

### 13.2 进入详细设计前需要确认

- 轮式机器人的具体型号、底盘轮型与运动学约束、机械臂/末端执行器配置、SDK 和计算资源。
- 所有现有技能 API 的真实签名、同步/异步方式和返回结果。
- 哪些门、物品、区域和交互动作属于允许集合。
- 高风险动作的准确分类和确认有效期。
- 嗅觉传感器的输出格式、类别能力和校准方式。
- 末端执行器触觉能够提供压力、接触、夹持力、滑移中的哪些信息。
- 底盘最大速度/加速度、制动距离、越障高度、允许坡度、最小通道宽度、转弯半径和额定载荷。
- 机械臂工作空间、整机稳定包络、运输姿态以及底盘与机械臂是否允许并发运动。
- VLM/LLM 是云端部署、边缘部署还是混合部署。
- 每类验收任务的超时与最大重试次数。
- 会话开始方式、唤醒词、无交互超时时间和是否允许免唤醒连续对话。
- 多人同时交互时的主说话者选择和排队策略。
- 原始音频、转写文本和对话日志的保存及隐私策略。
- 首选 LLM 的上下文窗口、输出 token 上限和准确分词器，以校准默认 8000 输入 token 预算。

## 14. 推荐实施顺序

1. 定义 `WorldState`、`DialogueState`、`TaskState`、`SystemState` 的类型、版本和唯一写入者，以及统一事件通道。
2. 定义技能注册表、Provider 生命周期、依赖与资源模型、版本化 `CapabilitySnapshot`、统一 `ActionResult` 和模拟技能后端。
3. 实现能力运行时的可用性计算与状态传播，并实现用途化 `ContextBuilder`、字段 TTL、相关性选择、token 预算与完整 JSON 裁剪、只读 `AgentContext`、实体修订号和调用审计日志。
4. 实现不依赖 LLM 的任务执行器，完成计划校验与接受、动作生命周期、Effect 记录与清理、Commit Point、受安全约束的补偿、有限重试、取消、资源仲裁和 `ReplanRequest`。
5. 接入语音识别、语音合成和对话管理器，实现有界最近轮次、对话摘要、结构化 Goal 槽位、焦点实体、绑定式确认、会话清理，以及 `Goal`、`GoalRevision` 和高优先级停止事件。
6. 接入无状态任务规划器，为各调用用途使用版本化固定提示和输出 Schema，并限定 LLM 只能生成绑定上下文/能力/实体版本的 `TaskPlanProposal` 或澄清请求，不得直接调用技能或写入状态。
7. 接入 RGB/深度感知和 VLM，完成实体 ID、地图坐标和 `WorldState` 的关联。
8. 接入轮式导航、朝向和交互动作等低风险技能，跑通计划接受、执行、观察刷新和重规划闭环，并验证台阶/跌落边缘、坡度与制动保护。
9. 接入抓取、触觉确认、递交和门操作，并增加安全监督、禁区和高风险确认流程。
10. 增加状态所有权、计划与实体版本、Provider 与依赖失效传播、Effect 清理、Commit Point、补偿安全、模型离线、上下文预算、摘要冲突、提示注入、跨会话隔离、确认错绑、任务打断、任务修改和交互反馈测试。
11. 建立冻结测试集、场景回放和端到端成功率评估。

## 15. 一句话产品定义

> 一个面向受控展厅轮式移动操作机器人的交互式任务智能中枢：通过多轮对话理解用户，通过 VLM 理解环境，由 LLM 提出受约束任务计划，以分权状态和只读上下文保持事实一致性，并由确定性执行器与安全层接受、编排和约束轮式移动、机械臂操作及其他物理动作。
