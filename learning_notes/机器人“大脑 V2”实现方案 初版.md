# 机器人“大脑 V2”实现方案 初版

# 



> 基于当前 `decision_center` 大脑架构现状、《大脑V2目标》，并结合论文  
> 
> 

\> **A Programming Paradigm for Spatiotemporal Composability**  

> 对现在大脑进行架构升级。
> 
> 
> 
> 本文区分两类内容：
> 
> 

\> \- **论文直接启发**：来自论文提出的 Revertible Effects、Reactive Coeffects、Unified Context、Component Lifecycle、Service Broker、Capability\-based Access Control、Declarative Reconciliation / HMR 等思想。

\> \- **V2 工程映射**：将上述思想映射到机器人 WorldState、Skill、Planner、Task Executor、Memory 和真机/仿真体系中的工程建议。该映射属于本方案的架构设计，并非论文直接给出的机器人实现。

# **1\. 核心结论**



大脑 V2 不应该只是：



> 一个更大的 LLM、更多 Agent、更多 Prompt 和更多剧本。
> 
> 



更合理的目标是形成三个层次：



```Plain Text
┌──────────────────────────────────────────────┐
│              Cognitive Layer                 │
│      “机器人现在应该理解什么、做什么？”       │
│                                              │
│ WorldState / Situation / Memory / Planner    │
│ Salience / Context / Proactive Intelligence  │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│               Brain Runtime                  │
│      “这些能力怎样安全、动态地组合运行？”      │
│                                              │
│ Runtime Context                              │
│ Reactive Capability Graph                    │
│ Component Lifecycle                          │
│ Effect / Commit / Compensation               │
│ Provider / Broker / Capability Control       │
│ Declarative Configuration / Reconciliation   │
└──────────────────────┬───────────────────────┘
                       ↓
┌──────────────────────────────────────────────┐
│               sasd Runtime                   │
│        “身体怎样实时、可靠、安全执行？”         │
│                                              │
│ Thalamus / State Machine / Interrupt         │
│ Speech / Hardware / Cerebellum / Navigation  │
└──────────────────────────────────────────────┘
```



因此，大脑 V2 的一句话定位更新为：



\> **以 WorldState 为认知基础、以 Reactive Capability Graph 为实时能力边界、以 Memory 保持认知连续性、以 Planner 负责高层目标分解、以 Brain Runtime 管理依赖/生命周期/副作用、以 sasd 作为实时执行底座的具身智能认知架构。**



**\-\-\-**



# **2\. 为什么这篇论文适合借鉴到 V2**



论文研究的不是“机器人如何思考”，而是：



> 一个系统由大量动态组件组成时，如何保证这些组件能够在运行时安全地加载、卸载、替换、依赖和恢复。
> 
> 



论文将动态可组合性分成两个维度：



## **2\.1 Temporal Composability**



时间可组合性关注：



> 一个组件被卸载后，它对系统产生的内部副作用能否被完整、按序地撤销。
> 
> 



论文使用：



```Plain Text
Revertible Effects
```



来描述这种能力。



**\-\-\-**



## **2\.2 Spatial Composability**



空间可组合性关注：



> 一个组件依赖哪些环境能力；这些依赖出现、消失或被替换时，组件是否能够自动激活、失活或重新绑定。
> 
> 



论文使用：



```Plain Text
Reactive Coeffects
```



来描述这种能力。



**\-\-\-**



## **2\.3 为什么与机器人 V2 高度相关**



大脑 V2 会逐渐拥有：




随着这些模块增加，真正困难的问题会逐渐从：

> “这些能力之间怎样安全组合？”
> 
> 



因此论文最适合用于补充 V2 的：



```Plain Text

```

```Plain Text

```

# **5\. 核心原则**



## **5\.1 LLM 不直接控制硬件**



继续保留当前 sasd 的核心原则：



> 所有真实动作最终都经过统一执行入口。
> 
> 



```Plain Text
LLM
 ↓
Structured Plan
 ↓
Validator
 ↓
Task Executor
 ↓
Brain Runtime
 ↓
sasd Thalamus
 ↓
Hardware
```



LLM 负责：



- 理解自然语言

- 推断隐含需求

- 生成计划

- 解释

- 澄清

- 自然表达

确定性系统负责：



- 能力存在性

- 前置条件

- 权限

- 安全

- 资源互斥

- Task State

- 完成判断

- rollback / compensation

- 中断

**\-\-\-**



## **5\.2 认知能力增加，不等于 LLM 调用次数增加**



V2 的主要增强应来自：



```Plain Text
更多结构化 State
更多本地规则
更多依赖声明
更多事件驱动
更精确 Context
```



而不是：



```Plain Text
Situation LLM
→ Memory LLM
→ Planner LLM
→ Validator LLM
→ Response LLM
```



普通 Turn 的关键路径尽量保持：



> 默认最多一次远程 LLM 推理。
> 
> 



复杂任务再进入 Planner Slow Path。



**\-\-\-**



# **6\. WorldState：机器人对“当前世界”的结构化认识**



## **6\.1 WorldState 与论文 Unified Context 的关系**



二者相似，但不应该等同。



论文 Unified Context 主要承担：



```Plain Text
组件共享状态
依赖
Effect
生命周期
```



机器人 WorldState 主要承担：



```Plain Text
当前人物
物体
环境
机器人姿态
位置
任务
对话者
```



因此建议进一步抽象：



```Python
BrainContext:
    world: WorldState
    capability: CapabilityContext
    task: TaskContext
    memory: MemoryContext
    runtime: RuntimeContext
```



外部可以通过统一 `BrainContext` 访问，但内部保持清晰边界。



**\-\-\-**



## **6\.2 WorldState 示例**



```YAML
robot:
  location: frontdesk
  state: conversation
  battery: 0.73

  hands:
    left: free
    right: free

environment:
  temperature:
    value: 35
    unit: C
    confidence: 0.98
    timestamp: 2026-08-15T14:30:00
    ttl: 10

people:
  - id: person_1
    distance: 1.4
    position: front_left
    carrying:
      - backpack

objects:
  - id: backpack_1
    owner: person_1

conversation:
  speaker: person_1
  last_utterance: 今天真热啊

task:
  active_task: null
```

# **7\. Situation Engine：从事实到“情景”**



高情商不是 Prompt 写得更温柔，而是：



```Plain Text
事实
 ↓
情景判断
 ↓
用户可能需要什么
 ↓
我现在能帮助什么
 ↓
选择合适的回应策略
```



例如：



```Plain Text
User:
今天真热啊

WorldState:
temperature = 35
user_has_backpack = true
```



Situation：



```JSON
{
  "facts": [
    "室内温度35℃",
    "用户携带背包"
  ],
  "inference": [
    "用户可能感觉炎热"
  ],
  "candidate_opportunities": [
    "offer_water",
    "offer_storage"
  ]
}
```



但是否真的能 offer water，不由 Situation Engine 决定。



需要进一步查询：



```Plain Text
Reactive Capability Graph
```

# **8\. Salience / Context Selector：眼力见的核心**



机器人不能：



> 看到什么就说什么。
> 
> 



建议：



```Plain Text
Salience =
    Conversation Relevance
  + Freshness
  + Confidence
  + Actionability
  + Safety Importance
  - Disturbance Cost
```



优先级：



|Level|类型|示例|
|---|---|---|
|P0|Safety|危险气体、碎玻璃|
|P1|Task\-critical|“那个”对应哪个物体|
|P2|Helpful|天热 \+ 可拿水|
|P3|Background|普通衣服颜色|



注入：



```Plain Text
P0 → 强制
P1 → 强制
P2 → 条件
P3 → 默认不注入
```

# **9\. 从 Skill Registry 升级为 Reactive Capability Graph**



这是结合论文后最重要的更新之一。



原设计：



```Plain Text
Skill Registry
=
静态登记机器人会什么
```



更新为：



```Plain Text
Reactive Capability Graph
=
根据当前 Provider、依赖、资源和系统状态实时计算机器人“现在能做什么”
```



**\-\-\-**



## **9\.1 Reactive Coeffects 的工程映射**



论文提出：



> 组件声明自己的环境依赖；依赖满足时激活，依赖消失时失活。
> 
> 



映射到机器人：



```YAML
skill: fetch_water

requires:
  - navigation
  - vision.object_detection
  - arm.right
  - gripper
  - map.water_station
```



当前：



```Plain Text
navigation              READY
vision.object_detection READY
arm.right               READY
gripper                 READY
map.water_station       READY

=> fetch_water AVAILABLE
```



机械臂掉线：



```Plain Text
arm.right FAILED

=> fetch_water UNAVAILABLE
=> fetch_parcel UNAVAILABLE
=> handover UNAVAILABLE
```



Planner 不需要等执行失败后才发现问题。



**\-\-\-**



## **9\.2 Capability Graph**



```Plain Text
vision.object_detection
                          │
                          ↓
                      locate_object
                          │
        ┌─────────────────┴────────────────┐
        ↓                                  ↓
    gripper                             navigation
        ↓                                  ↓
      pick                              walk_to
        └──────────────┬───────────────────┘
                       ↓
                  fetch_water
                       ↓
                   serve_user
```



底层 Provider 状态变化：



```Plain Text
Provider
  ↓
Capability
  ↓
Composite Skill
  ↓
Recipe
```



自动向上传播。

## **9\.3 SkillSpec 更新**



建议：



```Python
SkillSpec(
    name="fetch_water",
    version="1.2",

    description="为用户取水并交付",

    parameters={
        "target_person": "PersonRef"
    },

    requires={
        "navigation": ">=2.0",
        "vision.object_detection": ">=1.0",
        "arm.right": ">=3.1",
        "gripper": ">=1.4",
        "map.water_station": ">=1.0",
    },

    resources=[
        "legs",
        "right_arm",
        "gripper"
    ],

    effects=[
        "robot.location",
        "right_hand.state",
        "object.location"
    ],

    effect_policy="compensatable",

    timeout=120,
    interruptible=True,
    risk_level="medium",

    capabilities_required=[
        "navigation.goto",
        "vision.locate",
        "arm.pick",
        "arm.handover"
    ]
)
```



相比原版新增：



```Plain Text
version
requires
effects
effect_policy
capabilities_required
```

# **10\. Capability / Dependency 不能只靠名称匹配**



论文专门指出动态组件可能出现：



```Plain Text
Interface Drift
Key Collision
```



机器人同样存在。



例如：



```Plain Text
navigation.goto v1

goto(target_name: str)
```



升级后：



```Plain Text
navigation.goto v2

goto(target: Pose, tolerance: float)
```



如果仍只靠：



```Plain Text
key = "navigation.goto"
```



Planner / Skill 可能认为依赖仍然满足，但执行已经不兼容。



因此 V2 Capability 建议至少声明：



```Plain Text
namespace
name
version
schema
provider_id
status
```



例如：



```YAML
capability:
  namespace: jos.navigation
  name: goto
  version: 2.1
  schema: NavigationGotoV2
  provider_id: jos_real_01
```

# **11\. Component Lifecycle：统一模块生命周期**



论文的 Cordis 使用：



```Plain Text
LOADING
ACTIVE
UNLOADING
INACTIVE
```



V2 工程上建议扩展成：



```Plain Text
UNAVAILABLE
LOADING
READY
BUSY
DEGRADED
UNLOADING
FAILED
```



注意：



> `DEGRADED / FAILED` 是 V2 工程扩展，不是论文形式模型原状态集合。
> 
> 



**\-\-\-**



## **11\.1 示例**



```Plain Text
ArmProvider
    READY
      ↓
PickSkill
    READY
```



机械臂断开：



```Plain Text
ArmProvider
    FAILED
      ↓
PickSkill
    UNAVAILABLE
      ↓
FetchWaterRecipe
    UNAVAILABLE
```



这样机器人不会出现：



> 语言上说“我帮您拿”，身体上却根本没有可用机械臂。
> 
> 



**\-\-\-**



## **11\.2 生命周期与依赖联动**



```Plain Text
Provider ACTIVE
      ↓
Capability AVAILABLE
      ↓
Skill READY

Provider UNLOADING
      ↓
Capability WITHDRAWING
      ↓
Dependent Skill stops accepting new task
      ↓
Drain / cancel in-flight task
      ↓
Provider unload
```

# **12\. Task Executor：引入 Effect Tracking**



论文 Revertible Effects 的核心思想：



> 改变系统状态时，同时记录如何恢复。
> 
> 



这对 Task Executor 非常有价值。



**\-\-\-**



## **12\.1 Effect Stack**



例如：



```Plain Text
Task:
把物体放到桌子上

1. reserve(right_arm)
2. lock(target_object)
3. walk_to(object)
4. pick(object)
5. walk_to(table)
6. place(object)
```



内部 Effect：



```Plain Text
reserve(right_arm)
 inverse → release(right_arm)

lock(target_object)
 inverse → unlock(target_object)

subscribe(object_tracking)
 inverse → unsubscribe(object_tracking)
```



执行时：



```Plain Text
Effect A
Effect B
Effect C
```



同时形成：



```Plain Text
Undo C
Undo B
Undo A
```



失败时按 LIFO 恢复。



**\-\-\-**



# **13\. 机器人不能只依赖“回滚”：引入 System Boundary**



论文指出：



> 并不是所有作用于外部环境的动作都能够真正恢复。
> 
> 



这对机器人比普通软件更重要。



因此 V2 应明确区分：



```Plain Text
INTERNAL STATE
PHYSICAL WORLD / EXTERNAL WORLD
```



**\-\-\-**



## **13\.1 Effect Type**



建议每个动作声明：



```Plain Text
REVERSIBLE
COMPENSATABLE
IRREVERSIBLE
```



例如：



|Action|Type|示例处理|
|---|---|---|
|reserve arm|REVERSIBLE|release|
|register callback|REVERSIBLE|unregister|
|task lock|REVERSIBLE|unlock|
|navigation|COMPENSATABLE|return / stop|
|pick object|COMPENSATABLE|place back if possible|
|place object|COMPENSATABLE|move back if safe|
|speak|IRREVERSIBLE|只能纠正，不能撤回|
|send message|IRREVERSIBLE|可能补发更正|
|press physical button|IRREVERSIBLE / COMPENSATABLE|依场景|
|emergency stop|IRREVERSIBLE in current task|任务直接终止|

# **14\. Commit Point**



对于外部不可逆 Effect，在执行前增加 Commit Point。



```Plain Text
Plan
 ↓
prepare
 ↓
navigate
 ↓
locate
 ↓
approach
 ↓
────────── COMMIT POINT ──────────
 ↓
pick / press / send / submit
```



Commit Point 前进行：



```Plain Text
Capability Check
Safety Check
Freshness Check
Confidence Check
Resource Check
User Confirmation（必要时）
```



**\-\-\-**



## **14\.1 示例**



用户：



> 帮我把桌上的盒子拿走。
> 
> 



在：



```Plain Text
walk_to(table)
locate(box)
```



阶段都不需要用户二次确认。



在：



```Plain Text
pick(box)
```



之前如果视觉发现：



```Plain Text
多个高度相似盒子
confidence = 0.58
```



则：



```Plain Text
Commit blocked
→ Clarify
```



机器人：



> “您说的是左边这个黑色盒子吗？”
> 
>

# **15\. Compensation：物理世界中的“反向动作”**



软件 Effect 可以：



```Plain Text
undo
```



物理动作很多时候只能：



```Plain Text
compensate
```



因此 Task Executor 增加：



```Python
StepResult:
    status
    effect_type
    compensation
    observation
```



例如：



```Python
pick(box)

compensation:
    place_back(original_pose)
```



但 Compensation 也必须重新检查：



```Plain Text
当前环境是否允许
原位置是否仍空闲
人是否进入危险区
物体是否损坏
```



不能假设 Compensation 永远安全。

# **16\. Task State Machine**



统一任务状态：



```Plain Text
PENDING
VALIDATING
RUNNING
WAITING_USER
WAITING_DEPENDENCY
COMPENSATING
SUCCESS
FAILED
INTERRUPTED
```



任务执行：



```Plain Text
Plan
 ↓
Validate
 ↓
Step
 ↓
Execute
 ↓
Observe
 ↓
Success?
 ├─ yes → next
 └─ no
      ↓
    classify failure
      ├─ retry
      ├─ wait dependency
      ├─ fallback
      ├─ compensate
      ├─ replan
      └─ fail
```

# **17\. Provider / Consumer / Service Broker**



论文 Service Multiplexing 对 V2 的真机/仿真架构非常有价值。



不要：



```Python
if simulation:
    jos_sim.goto(...)
else:
    jos_real.goto(...)
```



而应该：



```Plain Text
NavigationService
       │
       ├── JOSRealProvider
       ├── JOSSimProvider
       └── MockNavigationProvider
```



Planner / Skill 只依赖：



```Plain Text
navigation.goto
```



而不关心具体实现。



**\-\-\-**



## **17\.1 Real / Sim / Mock**



```Plain Text
profile=real
```

# **40\. 最终结论**



结合论文以后，大脑 V2 的设计重点从：



```Plain Text
“如何让机器人拥有更多能力”
```



进一步升级为：



```Plain Text
“如何让机器人拥有一组能够动态组合、实时感知可用性、
可安全执行、可失败恢复、可切换实现、可持续扩展的能力体系”
```



论文对 V2 最大的三个启发是：



### **1\. Reactive Capability，而不是 Static Skill List**



机器人要知道的不是：



> “理论上我会什么。”
> 
> 



而是：



> “此刻我真正能做什么。”
> 
> 



**\-\-\-**



### **2\. Effect / Compensation，而不是 Plan 完就直接执行**



每个任务步骤都必须考虑：



```Plain Text
它改变了什么？
能不能撤销？
不能撤销时如何补偿？
什么时候进入 Commit Point？
```



**\-\-\-**



### **3\. Component Runtime，而不是不断向 sasd 堆功能**



未来新增：



```Plain Text
Skill
Memory
Planner
Provider
Proactive Module
Simulation
```



都应该成为受 Runtime 管理的组件，而不是继续向单体主循环追加新的：



```Plain Text
if / elif
global variable
background task
manual cleanup
```



最终，大脑 V2 应该实现两个闭环：



```Plain Text
认知闭环：
Perception
→ WorldState
→ Situation
→ Planning
→ Action
→ Observation
```



以及：



```Plain Text
运行时闭环：
Dependency
→ Activation
→ Effect
→ Execution
→ Withdrawal / Failure
→ Recovery / Compensation
```



**第一个闭环让机器人越来越“像人在思考”。**



**第二个闭环让越来越复杂的大脑仍然能够稳定运行。**
